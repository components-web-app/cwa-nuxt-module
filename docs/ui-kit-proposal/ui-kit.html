CWA Admin UI Kit Proposal v3 · #236 · UI kit only

The admin UI kit, v3

Every control is shown here in the state it will ship with. Only the kit is covered: how components declare their fields, styles and UI variants is a separate job. The menus, popovers, bar, modal and list all work, so try them with a mouse, a keyboard and a phone.

New in v3, after review:

  • Modals and pages edit a local copy and keep a Save button. Changed fields and tabs are marked, Save counts the changes and sends only those, errors from Save go on their fields, and a 412 asks per field which version to keep.
  • The page modal has tabs again (Details, Routes, Info, then page data tabs), including how they behave while creating.
  • The bar's status and primary action sit in the tab row on every tab, desktop and phone.
  • Only the innermost control under the pointer shows hover: stepper buttons, a chip's ×, clear buttons and status glyphs have their own shade, and the field's hover steps aside.
  • Textareas grow with their text up to 8 lines, with no resize handle.
  • Lists filter by type with square coloured toggles (Static blue, Dynamic yellow) and a matching dot per row; no more per-row thumbnails.
  • A failed save offers Retry and Reset. Undo is kept for things that happened.
  • A sliding tab indicator and calm micro-animations, all off under reduced motion.

Still true from v2:

  • Filled fields, no borders. A line appears only for focus (blue ring) or another editor (their colour).
  • Square everywhere. The toggle switch is the only rounded control.
  • Solid status glyphs: triangle, diamond and filled circles, each with a knocked-out mark.
  • One error pattern and one info pattern per surface. There are no hover tooltips on fields. Info opens in place in forms, so it never covers a field.
  • The link input is now the either/or group: choosing one option clears the others in the same save.
  • Friendlier spacing, a rebuilt modal form layout, a list on one grid, and phone layouts for all of them, with 44px touch targets.

2 · Select, multi-select and search menus

These follow the page theme. Open them with a click, a tap, or Arrow Down. Arrow keys move the highlight, typing jumps (select) or filters (search), Enter picks and Escape closes. When the window is narrower than 640px, menus open as a bottom sheet with the search pinned at the top, anything already typed carried into it, and the chosen styles shown as chips under the search. The sheet sits above the on-screen keyboard. In the page search, type fail to see a failed load.

In the bar a multi-select shows the first choice and “+N”, and lists the chosen options first when it opens. Disabled options give their reason on a second line, never on hover.

3 · Errors and info

Modals and pages show what Save returned: the message goes on the line below the field, linked with aria-describedby, and a conflict asks which version to keep. A client check (a bad URL) shows the same way before anything is sent. The bar has no room for a line, so the field's fill is tinted and its glyph is a button: click or tap it to open the message and its actions. Info is an opt-in ⓘ straight after the label. In a form it opens a note in place, under the label, and the field moves down so nothing is covered. In the bar it opens a popover titled with the field's name, with a close button. Use it only when a field's effect is not obvious from its label. Inline actions are text buttons with a 44px tap area; popovers and alerts use real buttons.

A failed save offers Retry and Reset (back to the last saved value). In the real bar the pinned status in the tab row also reads “1 not saved →” and the tab gets the triangle, so an error can be seen from any tab (see section 5).

4 · The either/or field group

A resource that stores exactly one of several fields, such as a link that is a route or a rawPath. The segmented control only chooses which field is shown, and switching saves nothing. In the bar, committing a value saves it and clears the other options' fields in the same request, and Undo stays available until your next edit. In a modal the same change goes into the local copy, and Save sends it, with the clearing, in one request. CwaUiLinkInput is this group with Page and URL already set up.

5 · The manager bar

The bar is one row and never stacks. The row scrolls sideways with fades at its edges; with a mouse, arrows also appear at a hovered edge, and they hide while a field has focus. Focusing a field scrolls it fully into view, label included. The status and the primary action are pinned in the tab row, top right, on every tab; they never move into the field row. Type in Title to see it save. Description is edited on the page: its button scrolls to the text and focuses it. Mia's flag sits in a layer above the bar, on the field's top edge, so it never covers the tabs and the bar's height never changes. When you type in a field Mia is in, the flag stays up and reads “Mia is editing this too”.

On a phone

The same bar with 2.75rem controls and no arrows. The status stays in the tab row as a glyph and a short word (Draft, Saving…, Saved, 1 not saved), beside Publish, so the field row has the full width. Fields are sized so the next one peeks in, and the row snaps to fields.

6 · Modals

A modal edits a local copy and keeps a Save button. Nothing is sent as you type. A changed field says “Unsaved” after its label and shows the solid dot in its status slot, its tab shows a dot, and Save counts the changes. Save sends only the changed fields, in one request per resource. Errors returned by Save go on their fields, linked below them, and each tab holding one gets the triangle and is opened. If someone else saved first (a 412), nothing is saved and each field you both changed asks which version to keep. Creating uses the same button and the same flow.

Layout: a label, 0.375rem, the field, 0.5rem, the helper line; fields 1.5rem apart; sections 2.5rem apart with space and no rules. The header, the tabs and the footer stay put while the body scrolls. Below 640px the dialog fills the screen, Delete moves to the header's ⋯ menu, and Cancel and Save share the footer row.

7 · Lists

Every list uses one grid, and the header row uses the same columns, so badges, dates and actions line up down the page. The whole row is the link. Rows are 4rem tall when they have two lines. There are no per-row thumbnails: a small dot after the name gives the page's type, Static (blue) or Dynamic (yellow), and the toggles above the list filter by it. A toggle is a square filled button with its colour as a dot when off, and filled in that colour with a check when on; none on shows every type. Below 768px a row becomes title and ⋯, with the status dot and word first on the second line and the path last, so only the path is cut. On a phone the toggles and sort share one scrolling row, and row actions open as a bottom sheet. Search, the filters and the checkboxes work.

8 · Toasts and inline save feedback

A routine save is shown in the field, never in a toast. Toasts are for things that happened away from a field: a background failure, a field in error that was unmounted, an undo. A failed save offers Retry and Reset (Retry all and Reset all for several), never Undo. Success and info toasts go after 4 seconds, warnings after 6; errors and toasts with actions stay until dismissed. On a phone toasts sit at the top, so they never cover the bar.

9 · Open questions for Daniel

  1. Page data fields. Page data has no SFC, but its fields should still be easy to configure for the page data modal. Where that configuration lives is part of the separate configuration job. The kit only needs the modal layout in section 6 to render whatever is declared. Still open.
  2. Palette. Can stone-200 (the light field fill), blue-400, blue-700, amber-700, lime-800, red-700 and red-400 be approved, or should they be replaced?
  3. Filled fields and WCAG 1.4.11. Against the surface, a field's fill is 1.7:1 in dark and 1.3:1 in light. The mitigations are an always-visible label, 4.5:1 value and placeholder text, 3:1 glyphs and a forced-colors outline. Is that acceptable, or should the dark fill go to stone-600 (2.3:1) and look heavier?
  4. field="…" shorthand on kit inputs inside a tab, with :model kept: yes or no?
  5. Model names: are state, retry and reset on the model, the updateResource result object, and fieldStates stored next to apiState in the resources store the right names?
  6. Bottom-sheet menus on phones: yes, or keep anchored popovers everywhere?
